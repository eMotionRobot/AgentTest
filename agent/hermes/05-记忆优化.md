# 专题：记忆优化（Memory Optimization）

> 本文拆解 Hermes Agent 的多层记忆体系与上下文工程，对比 OpenClaw 的记忆模型。重点：**冻结快照保护前缀缓存、辅助模型上下文压缩、FTS5 跨会话检索、可插拔记忆后端、辩证式用户建模**。

---

## 1. 记忆的分层（Hermes）

Hermes 的"记忆"不是单一概念，而是多层协同：

```text
  ┌─────────────────────────────────────────────────────────────┐
  │ ① 会话内上下文（短期）：当前对话消息 + 上下文压缩            │
  ├─────────────────────────────────────────────────────────────┤
  │ ② 持久声明性记忆（中期）：MEMORY.md（Agent 笔记）            │
  │                          USER.md（对用户的认知模型）         │
  ├─────────────────────────────────────────────────────────────┤
  │ ③ 程序性记忆：Skills（详见 04-skill技能进化.md）             │
  ├─────────────────────────────────────────────────────────────┤
  │ ④ 历史会话（长期）：SQLite SessionDB + FTS5 全文检索         │
  ├─────────────────────────────────────────────────────────────┤
  │ ⑤ 可插拔记忆后端：honcho / mem0 / supermemory…（向量/图等）  │
  └─────────────────────────────────────────────────────────────┘
```

---

## 2. 持久记忆：MEMORY.md / USER.md 与"冻结快照"

`tools/memory_tool.py` 提供有界、文件支撑、跨会话持久的记忆，分两个存储：

| 文件 | 内容 |
|------|------|
| `MEMORY.md` | Agent 自己的笔记与观察（环境事实、项目约定、工具怪癖、学到的东西） |
| `USER.md` | Agent 对用户的认知（偏好、沟通风格、期望、工作习惯） |

设计要点（**记忆优化的精髓**）：

1. **冻结快照（Frozen Snapshot）模式**：两个文件在**会话开始时**作为快照注入系统提示。**会话中途写入会立即落盘（持久）**，但**不改变本次会话的系统提示**——这样可**完整保留整个会话的前缀缓存（prefix cache）**。快照在下次会话开始时刷新。
   > 这是 Hermes 记忆优化的核心 trade-off：用"延迟一个会话生效"换取"全程不破坏 KV 缓存"，显著降低长会话成本与延迟。
2. **单一 `memory` 工具 + action 参数**：`add / replace / remove / read`。
3. **`replace`/`remove` 用短唯一子串匹配**（而非全文或 ID），更符合 LLM 的自然操作方式。
4. **字符（非 token）上限**：因为字符数与模型无关，便于跨模型一致管理；条目以 `§`（section sign）分隔，支持多行。
5. **行为指引写在工具 schema 描述里**：工具响应展示实时状态，系统提示保持稳定。

此外，**主动持久化**还由"后台复盘"驱动（见 [04](./04-skill技能进化.md)）：复盘提示会促使 Agent 把"用户透露的偏好/期望"写入记忆——即 README 所说的"nudges itself to persist knowledge"。

## 3. 上下文压缩（Context Compression）

长对话会超出上下文窗口，Hermes 用**辅助模型（便宜/快）摘要中段、保护头尾**来压缩。涉及 `agent/context_compressor.py` 与 `agent/conversation_compression.py`。

相对早期版本的改进（源码注释，已转述）：

- **结构化摘要模板**：带"Resolved / Pending 问题"追踪；
- **过滤安全的摘要前导语**：把先前回合当作"源材料"，避免被当成新指令；
- 用 **"Remaining Work"** 取代 "Next Steps"，避免被误读为"当前活动指令"；
- **迭代式摘要更新**：多次压缩间信息得以累积保留；
- **按 token 预算保护尾部**（而非固定消息条数）；
- **摘要前先廉价裁剪工具输出**（pre-pass）；
- **摘要预算按被压缩内容量缩放**。

压缩时的关键提示（`SUMMARY_PREFIX`，已转述）特别强调：摘要是"**仅供参考的历史交接**"，不要去回答/执行摘要里提到的、已处理过的请求；当前任务在"## Active Task"段落里，从那里精确续接；并提醒"你的持久记忆（MEMORY.md/USER.md）在系统提示中"。

启动时还有 `check_compression_model_feasibility`：探测辅助压缩模型的上下文窗口是否能容纳主模型的压缩阈值，必要时自动下调会话阈值，过小则硬拒绝。压缩动作完成后会切分 SQLite 会话、轮换 `session_id`，并通知上下文引擎/记忆后端。

## 4. 跨会话检索：SQLite FTS5（含 CJK 优化）

`hermes_state.py` 的 `SessionDB` 用 SQLite 持久化所有会话消息，并建立**全文检索**：

- `messages_fts`：标准 **FTS5** 虚拟表，用于快速文本检索；
- `messages_fts_trigram`：**三元组（trigram）FTS5** 表，专为 **CJK（中日韩）子串检索**设计——因为默认的 `unicode61` 分词器对中文不友好，三元组索引能支持中文子串匹配；
- 索引覆盖 `tool_name`、`tool_calls` 等字段；
- `session_search` 支持"发现形态"（锚定 FTS5 命中）与"滚动形态"（锚定任意消息 id），并用 **bookends（书挡）** 让长会话中任意位置的命中都能产出目标上下文；
- `_sanitize_fts5_query` 对用户输入做净化（FTS5 的 `"`、`(`、`)`、`*` 等特殊字符可能引发 `OperationalError`），并把带连字符/点号的词加引号。

> 结合 README："searches its own past conversations" + "FTS5 session search with LLM summarization for cross-session recall"——即**先 FTS5 召回历史片段，再用 LLM 摘要**，实现跨会话回忆。**对中文用户尤其友好**（trigram 索引）。

## 5. 可插拔记忆后端 + 辩证式用户建模

`agent/memory_manager.py` 统一编排各记忆 provider（实现 `MemoryProvider` ABC），生命周期钩子包括 `sync_turn()`、`prefetch()`、`shutdown()`、可选 `post_setup()`：

```python
# run_agent.py 中的单一集成点（示意）
self._memory_manager = MemoryManager()
self._memory_manager.add_provider(plugin_provider)         # 同时只允许一个外部 provider
prompt_parts.append(self._memory_manager.build_system_prompt())   # 系统提示
context = self._memory_manager.prefetch_all(user_message)         # 回合前预取
self._memory_manager.sync_all(user_msg, assistant_response)       # 回合后同步
self._memory_manager.queue_prefetch_all(user_msg)                 # 预取下次
```

内建 provider：honcho、mem0、supermemory、byterover、hindsight、holographic、openviking、retaindb。

**安全细节**：注入的记忆上下文用 `<memory-context>` 围栏标记，并配 `StreamingContextScrubber` 状态机，在流式输出中**跨 chunk 边界**也能剥离围栏标签与系统注记，防止"召回的记忆内容"泄漏到 UI 或被当成新用户输入——这是**记忆注入的提示注入防护**。

**Honcho 辩证式用户建模（dialectic user modeling）**：README 明确集成 [Honcho](https://github.com/plastic-labs/honcho)，用于跨会话"构建对你的认知模型"，让 Agent 对用户的理解随时间加深。

## 6. 对比：OpenClaw 的记忆模型

| 维度 | Hermes Agent | OpenClaw |
|------|--------------|----------|
| 持久记忆载体 | MEMORY.md + USER.md（冻结快照） | SOUL.md + MEMORY.md（Markdown 文件） |
| 缓存优化 | ✅ 冻结快照保护前缀缓存 | ⚠️ 文件注入，未见同等机制 |
| 跨会话全文检索 | ✅ FTS5 + 三元组（CJK） | ⚠️ 会话历史，无内建 FTS |
| 上下文压缩 | ✅ 辅助模型摘要 + 头尾保护 + 结构化模板 | ✅ `/compact` 命令 |
| 可插拔记忆后端 | ✅ 多种（向量/图等） | ⚠️ 以文件/会话为主 |
| 用户建模 | ✅ Honcho 辩证式 | ❌（靠 SOUL.md 人工维护） |
| 主动持久化 | ✅ 后台复盘"nudge"写入 | ❌ 人工维护 |

OpenClaw 的记忆哲学是**纯文本、可审计、人可读**：身份与记忆都存为 Markdown（SOUL.md / MEMORY.md），配合会话模型与 `/compact`。有第三方文章把它描述为"短期上下文 + 中期 Markdown + 长期向量索引"的分层（[fast.io](https://about.fast.io/resources/openclaw-agent-memory-management-patterns/)，内容经转述）——但需注意这更多是**实践模式/可选搭配**，而非核心内建的自动闭环。

**一句话总结差异**：
- OpenClaw = **可审计的文件式记忆**，简单、透明、可控，但留存与召回靠人工与会话历史；
- Hermes = **工程化的多层记忆**：冻结快照护缓存、FTS5（CJK 友好）跨会话召回、可插拔后端、Honcho 用户建模、后台主动持久化——更适合长期、低成本、随用随长的场景。
